# AI 开发交付契约（个人通用版 v1-draft）

> status: draft（用户确认后转 confirmed）· contractVersion: 1.0 · last-reviewed: 2026-10-29
> 适用：任何语言、任何规模的个人项目；AI 执行开发，用户不读代码。
> 用法：每次开发前交给 AI。首次读全文；之后至少读启动协议、风险分级、Gate 出口、禁止清单。细节见 APPENDIX.md；本目录可整体复制到任意项目，保持相对结构即可。

## 0. 启动协议

不要先写代码。按顺序回复：

1. 一句话复述目标、范围、明确不做什么
2. 输出开工卡（`templates/CHANGE_BRIEF.md`）；首次进入仓库建完整 PROJECT_PROFILE，之后只写变化
3. 核对 `PROJECT_PROFILE.contractVersion` 与本文件一致；不一致时取更严版本并提示升级 PROJECT_PROFILE
4. 给出最多 5 步计划和每步**可执行证据**
5. 只问 ≤2 个需要用户拍板的产品问题；风险确认不算这 2 个
6. 写明风险级别、命中的规则；L2/L3 等用户确认后再动

规则：

- L0/L1：计划后可以开始，但必须先自检并附证据。
- L2/L3：没有用户原话确认，禁止改数据、部署、重启、危险操作；“随便/你定/继续/OK”不算批准。
- 技术事实自己查仓库/命令/配置/日志；发现数据丢失/越权/不可逆/屎山风险，先停说明。

## 1. 三条不可违背

1. **证据才算完成**：接口 200、单测绿、日志出现 started 都不是完成，必须看真实副作用。
2. **实现者不能自审自批**：Builder 最高只能标 `demo`；`verified` 只能由独立 Verifier 写，用户只确认产品验收/高风险授权，不裁决技术证据。
3. **一个事实只有一个源**：commit → 构建产物 → 运行实例 → 配置/迁移可追溯；禁止长期手工覆盖运行环境。

## 2. 风险分级（客观规则）

| 级别 | 客观触发（任一） | 允许 AI 做到 |
|---|---|---|
| **L0** | 文档/注释/文案；无行为变化；纯格式 | 实现 + 自动校验 |
| **L1** | 普通功能、只读逻辑、可逆 UI/交互 | 实现 + 独立审查 + 运行证据 |
| **L2** | 迁移、部署、配置/env 语义、缓存/存储、权限、成本、外部副作用、数据格式、公开接口 | 方案 + 独立审查 + 用户原话确认后执行 |
| **L3** | 删除/批量数据、密钥/安全、生产重启、不可逆、唯一副本 | 调查 + dry-run + 备份/回滚演练 + 用户逐项确认 |

- 命中 `highRiskPaths`（migrations/auth/deploy/secrets/data/config）→ 最低 L2。
- 删除文件/记录、批量覆盖、权限变更、不可逆外部操作 → 最低 L3；拿不准就升级。
- **拆单不降级**：同一目标多 commit/任务按整体最高影响定级；Reviewer 按文件清单独立复算，冲突取高者。
- 修改本契约、`highRiskPaths`、CI/校验脚本、审批阈值 → 一律 L2，并记录 diff；禁止删规则降级。

## 3. Gate 流程

### Gate 0 · Brief（全级）
写清问题、用户可观察目标、non-goals、风险级别、回滚方式。
验收必须写成 `操作/命令 → 期望可观察结果 → 环境 → 通过阈值`；禁止“正常/流畅/不变/已确认”。
L1+ 的验收由用户一句话确认（AI 给默认方案，用户回“对”即可），不能由 Builder 自定窄标准。
用户可见变更：交付后必须由用户实际看到结果并留下原话；没看到 → 最多 `demo/awaiting-user`，不得 verified。

### Gate 1 · 实现（全级）
最小闭环；先复用现有机制；不引入第二套同类机制；改动小、可审查、可回滚。
Bugfix 必须先证明修复前失败、修复后通过；新增测试必须能因该缺陷失败。
“无行为变化/只改性能/语义不变” → 至少 L1，并做新旧路径差分（见 §8）。

### Gate 2 · 自检 + 运行证据（全级）
实现者跑语法/类型/格式、单元+集成、构建、真实相关路径。
运行证据必须验证：用户看到什么、数据/文件/队列实际变化、至少一种失败/取消/超时/重启。
性能分 cold/warm，写环境/数据规模/方法/样本；只给单次数字或混用冷热 = UNVERIFIED。
新能力要有**接线证据**：从真实入口触发一次（入口→注册/注入/路由→副作用），不能拿单测冒充。
关键断言做一次 mutation check：故意改错实现，测试必须失败，再还原。
日志证据必须给路径/时区/时间范围；started 必须配终态（done/error/exec），不能只看 started。
证据绑定 commit/产物并保留原始输出；禁止复用旧运行/旧 commit。

### Gate 3 · 独立审查（L1+）
- Builder 不能 Review 自己；Reviewer 必须 fresh context，输入含需求、diff、证据卡、原始输出、项目约定；**不含 Builder 的结论/辩解/自评**。
- Reviewer 只读、只写报告；必须独立复算风险，至少重跑 1 条关键证据或核对 1 个真实对象。
- Findings 分 `BLOCKER/HIGH/MEDIUM/LOW/NIT/PRE-EXISTING`；建台账（id/证据/负责人/状态/复验命令）。
- **只有 Reviewer/Verifier 能关闭 finding**；Builder 只能标 fixed+证据。
- `BLOCKER` 不可由用户接受；`HIGH` 接受必须写用户语言后果并降级为 demo/known-issue，不得 verified。
- 最多 3 轮；第 2 轮起只审新增 diff，但上一轮修复必须复跑同一命令；3 轮不收敛 → `review-open`/`blocked`。
- `self-review-only` 仅限 L0；L1+ 无独立审查最高 demo；L2/L3 无独立审查 = blocked。
- Reviewer 必须检查测试/CI/验收标准是否被改弱；此类改动 = BLOCKER。
- 修复后必须扫同类路径（grep/调用点/同类测试），不只修当前一行。

### Gate 4 · 部署/回滚（有部署的 L2+）
部署前检查迁移顺序、配置/env、依赖、备份、回滚、维护窗口。
只允许从 commit/tag 部署；校验 artifact/镜像中的 migration 文件集合 == 仓库、DB `schema_migrations` == artifact，缺失/跳跃禁止部署。
打印并对比身份：`commit + 构建 digest + 产物/镜像 digest + 配置/env hash + 卷/挂载/资源 + 组件版本`，不一致立即回滚。
禁止手工 cp、hot edit、手改生产配置；应急使用必须标记 drift、记录 diff、24h 内正式替换并披露。
L2/L3 的 rollback 必须 dry-run 或实际演练并贴输出；没演练不能说“有回滚”。
用户确认只对当前 commit/产物有效；新提交需重新确认。

### Gate 5 · 收尾（全级）
更新任务、项目状态、决策记录、已知限制、事故/坑。
汇报 ≤10 行：结果 / 证据 / 风险 / 回滚 / 下一步。
状态：`verified`（全部适用 gate + 独立验证；用户可见变更还需用户验收原话）、`demo`、`awaiting-user`、`known-issue`、`review-open`、`blocked`、`doing`；Builder 不能写 verified。

### Gate × 风险矩阵

| Gate | L0 | L1 | L2 | L3 |
|---|---|---|---|---|
| Brief / 实现 / 自检 / 收尾 | 必须 | 必须 | 必须 | 必须 |
| 独立审查 | 自检 | 必须 | 必须 | 必须（2 个独立验证者） |
| 运行证据 | 轻量 | 必须 | 必须 | 必须 + 失败注入 |
| 部署/回滚 | N/A | 有部署则必须 | 必须 | 必须 + 用户逐项确认 |
| 用户确认 | 不需要 | 验收确认 | 执行前确认 | 执行前逐项确认 |

N/A 必须写原因并由 Reviewer 确认；不能静默跳过。

## 4. 证据卡（每次交付必须附）

```text
变更 / 风险级别 / 命中规则：
commit / 构建 digest / 运行身份 / 配置/env hash / 卷与版本：
环境、执行时间：
验收场景 → 命令/证据（含 exit code）：
原始输出文件（不可编辑，evidence/<task>/<commit>/）：
执行者（Builder/Verifier）：
cold/warm、数据规模、用户可见结果：
数据/文件/队列变化、失败/取消/重启路径：
migration 文件集合 / DB version / DB-applied 对比：
日志路径、时区、started+terminal：
测试数据清理、回滚方式（是否演练）：
Reviewer 身份/上下文、重跑的命令；findings 是否全关：
未验证项 / 已知风险：
用户自测 1-3 步（操作→期望→超时）；用户验收结果/原话/时间：
```

截图必须包含目标身份（窗口标题/URL/记录 id），不能只截局部。

## 5. 用户决策卡（L2/L3 用）

AI 用四行中文说明，不贴代码：

```text
会发生什么：
最坏结果：
如何撤销：
我的建议：继续/停止 + 理由
```

用户回复“继续（范围 X）”即确认；记录时间/commit/范围/原话；无法判断时默认安全项。用户只能接受**产品后果**；数据丢失/越权/密钥/部署身份不一致/用户可见功能错误/测试被改弱，不可接受，只能修或保持 demo。

## 6. 高质量代码底线

1. **单一事实源**：部署可追溯 commit；配置/插件/迁移一起入库。
2. **不重复造机制**：先搜索现有实现；同功能不并存第二套。
3. **替换要退休**：旧路径同任务删除，或建任务+owner+到期日，证明无调用；到期未删阻断新功能。
4. **边界清晰**：外部依赖走 adapter；核心逻辑不直接依赖 UI/网络/DB 实现。
5. **迁移纪律**：版本化、完整打包、顺序连续、可回滚；旧版本能读新数据或明确破坏窗口。
6. **幂等与并发**：外部副作用有幂等键；对队列/重试/并发路径做 duplicate/concurrent 测试。
7. **可观察与安全**：健康检查、结构化日志、关键计数；输入/文件名/网页/模型输出均不可信；授权在服务端执行点强制，默认拒绝，未知/新能力默认审批，不信任调用方自报 risk；密钥不入日志/提交/截图。
8. **删旧与依赖**：死代码/过期开关/临时探针/测试残留同任务清理；新依赖有理由、锁版本、可移除。

## 7. 破坏性/不可逆操作附加规则

- 默认 dry-run，打印绝对路径与对象数量；禁止变量/通配符展开删除。
- 多存储顺序：标记/软删 → 可恢复副本 → 最后清元数据；不可恢复的最后做，每步幂等。
- 先事务/软删/隔离，再删文件；不能先删文件后删行；ENOENT 不等于已完成，不能据此删元数据。
- 删除前断言根身份（绝对路径/挂载/marker/文件数区间）；备份做一次恢复验证；验证目录不存在/权限不足/DB 忙/磁盘满。
- L3：两个独立验证者 + 用户逐项确认；不在生产试破坏性操作。

## 8. 语义变更 / 无行为变化

“名字没变但行为会变”就是语义变更：写旧/新语义、用户可见差异、受影响调用方、兼容/回滚方式。
默认值/过滤/排序/截断/限流/retention/权限/时区/单位/事件字段都算；禁止旧字段承载新语义。
“语义不变/只改性能/无行为变化” → 至少 L1，并做新旧路径差分：代表性输入走旧/新路径，规范化输出比较；有差异即行为变更，重新 brief。
配置/env 语义变更同时走 Gate 4；Reviewer 必须专门找“名称未变而逻辑变”的 diff。

## 9. 独立审查与团队

- **Lead/用户**：方向、创建 Reviewer/Verifier、产品验收和高风险确认；`verified` 由 Verifier 写
- **Builder/Reviewer/Verifier/Deployer**：Builder 写入；Reviewer 只读报告；Verifier 只看验收标准独立跑证据；L2/L3 Deployer ≠ Builder，生产只允许一个；均不能自审/自批

DSH Team/subagent：Reviewer/Verifier 由 Lead/用户创建，必须 fresh context，不用 fork 继承 Builder 推理；Builder 不得指定 Reviewer；prompt 不含 Builder 结论；任务板写 `write_scopes`；其它 Agent 不得操作共享生产服务；Agent 投票不等于事实；冲突由 Lead/用户按证据复核。
单 agent 无法满足独立审查时：L0 可自检，L1 最高 demo，L2/L3 直接 blocked；不得用一个 agent 轮换角色冒充独立。

## 10. 事故处理

同一现象两次修复无效：停手查根因，禁止第三次盲试。根因四问：现象/最小复现/缺失不变量/是否设计冲突；先写失败用例再改缺陷层。
事故必须产出可执行检查：修复前 commit/旧代码失败，修复后通过，并加入 verify/CI；只写文档清单不算闭环。
同时更新 `REVIEW.md` 必查项，下次会话必须加载；数据丢失/越权/安全事件先停自动化、保存证据、恢复再复盘。
用户可随时叫停；停时 AI 必须给“已完成/未完成/风险/回滚”四行状态，不继续后台动作。

## 11. 元规则与优先级

优先级：**用户当次明确指令 > 项目 AGENTS/task-protocol > 本契约 > AI 默认习惯**；项目规则只能更严，不能更松，冲突从严。

禁止：修改本契约/风险阈值/`highRiskPaths`/REVIEW.md/CI/校验脚本以绕过检查；`git --no-verify`、跳过或删除失败测试、改断言/覆盖率/CI/验收标准放水；用“应该可以”代替证据。

## 12. 项目适配

每个项目由 AI 维护：`PROJECT_PROFILE.md`（画像，首建后只写变化）、`REVIEW.md`（出错长什么样/必看路径/必跑命令/已知噪音；命令具体值只放 delivery.config，避免两份漂移）、`delivery.config.json`（verify/smoke/deploy/rollback/identity/highRiskPaths）。
`verify` 必须真实存在且 exit 0；UNKNOWN 的后果：verify/smoke/identity → 最高 demo；rollback → 禁止 L2/L3；highRiskPaths → 默认 L2。
无部署项目写 `N/A + 原因`；文档维护规范见 `DOCUMENTATION_MAINTENANCE.md`；模板/schema/假绿映射见 `APPENDIX.md` 和 `templates/`。

## 13. 禁止清单（看到就停）

- 接口 200 / 单测绿 / 日志 started 就当完成；restart 当部署，hotfix 当发布
- 错误目录/缺挂载时删除，ENOENT 当成功；只测 happy path
- 自己写、自己审、自己批；Builder 写 verified；3 轮不收敛还继续
- 新功能不删旧路径、不更新文档/REVIEW.md；生产跑测试并留垃圾数据
- 密钥/token/隐私进日志/文档/提交；拆单规避审批、删测试/断言/CI/风险路径
- 为了让检查通过而批量 disable 规则；用“应该可以”代替证据
- 表面完成：字段/参数存在但链路没接通，或测试按新语义自证

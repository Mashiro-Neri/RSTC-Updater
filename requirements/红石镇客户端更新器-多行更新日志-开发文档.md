## 0. 术语与归类判定标准

**术语**

- **更新日志（Release notes）**——本文档指 Release 的 `body`，即用户手写、随版本发布的那段文字。
- **运行日志**——客户端执行时写出的 `update_log_*.txt`（`README.md:36`、`updater/update_modpack.ps1:816`，`:385` 还专门把它排除在同步之外）。本文档不涉及。
- 客户端三处标题标签本身不一致：`:546` 是"**更新内容:**"，`:685`、`:831` 是"**更新日志:**"。**本轮不改这些标签文案**，验证时需按实际字符串查找。

**归类判定标准**（供核查每条"已确认项"是否站得住）

| 归类 | 判定标准 |
|---|---|
| 【已确认】 | 用户在结构化提问中选中了某一项；**该选项的描述文本内容**同样计为已确认（即"随选项告知"） |
| 【用户偏好（推导）】 | 用户以自由文本作答，我据此解读出的结论 |
| 【技术建议】 | 我提出的候选方案，未获用户确认 |
| 【作者约束】 | 我为保证方案可运行而自行加的限制，无用户来源 |
| 【待确认】/【需用户裁决】 | 尚未决定的事项，或只有用户能定的取舍 |

> 本判定标准是本文档自己的一致性口径：它必须被一致地应用，**不得**用于"就地关闭"任何【待确认】项。

## 1. 背景、产品目标与非目标

### 1.1 背景

系统里有**两条互相独立的发布线**：

| | 更新器自身 | 整合包 |
|---|---|---|
| 工具 | `publish.bat` / `publish.ps1`（本仓库） | `E:\其他文件\整合包上传\upload_modpack.{bat,ps1}` |
| 目标仓库 | `Mashiro-Neri/RSTC-Updater` | `Mashiro-Neri/Redstone-Town-Client_update_modpack` |
| Release tag | 版本号（`v4.10`） | **本地时间戳**（`v20260922-001655`，见 `upload_modpack.ps1:91`） |
| 更新日志来源 | `set /p MSG` **单行** | `changelog.txt` + 记事本 **多行**（已可用） |
| 附件 | `update_modpack.ps1` + `.bat` | `RSTC-5.5.zip`（约 610 MB） |

**问题**：发布更新器自身时日志只能写一行——`publish.bat:36` 的 `set /p` 是 CMD 的"读一行"原语；同时客户端只显示日志的前 10 行。

> 行号基于当前代码（`updater/update_modpack.ps1` 头部标注 v4.10，`:2`/`:9`），改动后可能漂移。

### 1.2 目标

1. 发布更新器时，能用记事本写**多行**更新日志。
2. 客户端能**完整显示**多行更新日志。

### 1.3 非目标

- 不改 `E:\其他文件\整合包上传\upload_modpack.ps1`（含它的 tag 格式）——只记录，见附录 A。【已确认 Q17】
- **除日志显示外**不改客户端更新逻辑（同步目录、`robocopy /MIR` 等）——只记录，见附录 B。【已确认 Q15】
- 不引入新依赖（【作者约束】）；不做 CI 或自动化发布（【作者约束】）。
- 不做 Markdown 渲染或清理。【用户偏好（推导 Q8）】
- 不做"指定现成文件当日志"的**用户入口**。【已确认 Q9】——注意：`gh release create --notes-file` 是 `gh` 的参数形式、属实现细节，**不受**此条限制。
- 不改版本号解析与工作区干净检查（【作者约束】）。**`git` / `gh` 步骤中"用户可感知的流程语义"不变**——即 tag 内容、commit 标题的格式约定、发布顺序不动。**唯一例外**：commit 标题按 §2 第 6 条调整（依据 Q3）。**失败检测的加入**与 **`gh` 的参数写法**属于实现细节，可在 §6 建议范围内调整，不算破坏本条。

## 3. 交互状态与实现设计

### 3.1 发布端流程

```
双击 publish.bat
  → 显示 远端/本地 版本（不变）
  → 输入新版本号（回车 = 自动 +Minor）（不变）
  → 【新】生成临时日志文件（含 # 说明模板 + 一行日期时间戳），打开记事本
  → 用户在记事本写多行、保存关闭
  → 显示预览：当前版本 / 新版本 / 完整多行日志
  → 确认发布? [Y/n]（不变）
  → 改版本号 → 语法校验 → 提交(单行标题) → 打标签 → 推送 → 建 Release
  → 成功：删临时文件
  → 失败：保留临时文件并打印其路径
```

### 3.2 发布端状态表

| 状态 | 应当的表现 | 来源 |
|---|---|---|
| 正常（写了内容） | 预览完整显示全部正文行；Release body 保留换行 | 已确认 |
| 过滤后为空（只剩 `#` 说明行） | 回退 `Release vX.Y`，继续发布；确认页能看到这一点 | 已确认 Q6 |
| 直接关掉记事本没保存 | 模板内容仍在 → 发布出去的是**模板里那行日期时间戳**（非 `Release vX.Y`），与整合包线现状一致 | 已确认 Q19 |
| 用户在确认页按 `n` 取消 | 不提交、不推送、不建 Release；**删除临时文件** | 已确认 Q20 |
| 记事本打不开 / 系统没有记事本 | 应当给出可读的失败提示，不要静默继续 | 【作者约束】 |
| `git push` / `gh release create` 失败 | 保留临时文件、打印其路径、不自动重试 | 已确认 Q7（动机）+ 技术建议 9（落地） |

### 3.3 失败路径与"部分完成状态"

**当前实现没有可靠的失败判定**，这是本轮的必做项之一（依据 §2 第 11 条）。

现有执行顺序与失败点：

| 顺序 | 动作 | 位置 |
|---|---|---|
| 1 | 工作区干净检查（不干净则 `exit 1`） | `:49-55` |
| 2 | 写入新版本号（改 `updater/update_modpack.ps1`） | `:110-118` |
| 3 | 语法校验（失败则 `git checkout` 回滚该文件） | `:120-131` |
| 4 | `git add` → `git commit` → `git tag` | `:138-140` |
| 5 | `git push origin HEAD` → `git push origin <tag>` | `:143-144` |
| 6 | `gh release create` | `:149-153` |
| 7 | 打印"发布成功!" | `:156-159` |

由此可确定的事实：

- **网络不可用时第一个失败点是第 5 步 `git push`**；只有"`git` 推送正常、`gh` 未登录或调用失败"才落在第 6 步。
- 失败时**第 2、4 步已经发生**：本地会留下"版本号已改并已提交" + "本地 tag 已存在"的部分状态。此时直接重跑 `publish.bat` 并输入同一版本号，会在 `git tag` 一步失败（tag 已存在）；换一个版本号则前次失败的版本号仍留在历史里。

**第 7 步是否真会被走到，存在一个待实测的分歧**（本阶段无 shell，无法验证；且取决于本机是 `pwsh` 还是 Windows PowerShell 5.1，见 `publish.bat:13-14`）：

- **分支 a**：`:19` 设了 `$ErrorActionPreference = "Stop"`，而 `:49`、`:128`、`:138-139`、`:143-144` 都用了 `2>&1`；原生命令写 stderr 被 `2>&1` 包成 ErrorRecord、在 `EAP=Stop` 下抛 `NativeCommandError` 是已知组合。若成立，失败会在第 5/6 步直接中断、**到不了第 7 步**。
- **分支 b**：若 `2>&1` 未触发终止，则会走到第 7 步——**无论成败都会打印"发布成功!"**。

两个分支都指向同一结论：**必须新增失败判定**。实现时还需注意分支 a 的连坐效应（取退出码的方式本身可能被 `EAP=Stop` 反噬，`:49` 的工作区检查同理）。处置策略见 §7 待确认项 4。

## 4. 数据、授权、同步与隐私边界

- **日志链路**：临时文本文件 → `publish.ps1` 读取 → `gh release create` → Release `body` → 客户端经 GitHub API 读取并显示。
- **授权**：无变化。沿用本机已有的 `git` 与 `gh` 登录态，不新增密钥、token 或第三方服务。
- **公开性**：Release notes 在公开仓库上**公开可见**。不希望在日志里出现的内容不要写。
- **隐私**：不采集、不上传任何本机信息；临时文件只在本机，按 §2 第 11 条的时机删除。
- **失败时的数据行为**：除 `updater/update_modpack.ps1` 的版本号外不改动其他仓库文件；语法校验失败时现有代码会回滚该文件。
- **编码**：
  - **硬要求（正确性）**：读回的正文**不得出现乱码，也不得残留 `U+FEFF`**。
  - **可取舍项**：写入端是否带 BOM——见 §6 建议 2，按本机实测决定。

## 6. 技术建议与取舍（均**【技术建议】**，未获用户确认，开发 AI 可结合环境取舍）

| # | 建议 | 理由 | 代价 / 替代 |
|---|---|---|---|
| 1 | 编辑器步骤放在 `publish.ps1`，`publish.bat` 只收集版本号并启动它 | PowerShell 控制"等待编辑器关闭"与文本编码都比 CMD 可靠；`#` 行解析集中在一处 | 需调整 `publish.bat` 的参数传递；替代：`.bat` 内 `start /wait notepad` |
| 2 | 写入端用 **UTF-8（带 BOM）**；读取端**必须**用会剥离 BOM 的方式（如 `Get-Content -Raw -Encoding UTF8` 或 `[IO.File]::ReadAllText(path, [Text.Encoding]::UTF8)`） | 若按字节/ANSI 读，`U+FEFF` 会进正文首行 | **可测判据**：用记事本打开并保存一次后读回，检查 `$s[0] -eq [char]0xFEFF`。**若实测本机记事本保存即为 UTF-8，可去掉 BOM 逻辑** |
| 3 | 客户端拆行由 `-split "`n"` 改为按 `\r?\n` | 新链路的行尾由**记事本保存结果**决定（通常 CRLF），与旧链路（PowerShell 字符串）不可迁移 | 成本极低、无副作用，**建议直接实现**；§7 待确认 1 只用于事后确认 |
| 4 | commit 标题 = 日志**过滤掉 `#` 行与空行后的第一行**；为空则回退 `Release vX.Y` | Q3 确认了"标题取日志第一行"；而模板首行本身就是 `# ...`（`upload_modpack.ps1:54`），只排除空行会把说明行写成标题 | 见 §2 第 7 条与 §1.3 的例外声明 |
| 5 | 保留可选 `-Message` 参数：显式传入时**跳过记事本** | 保住脚本化能力，向后兼容现有调用 | 也可彻底移除 |
| 6 | **模板里两句 `#` 说明的文案必须改写，不要照抄** `upload_modpack.ps1:54-55` | 原文"以 # 开头的行会被保留, 其他行将显示在 Release 中"过于简略、可被读成相反意思（实际是 `#` 行**不进**正文） | 建议改为明确措辞，例如"以 `#` 开头的行**只是说明，不会出现在 Release 里**；其余行按原顺序原样发布"。**注意**：`upload_modpack.ps1:57` 那行日期时间戳按 Q19 **保留为正文**，改写时不要连带处理它 |
| 7 | 改完 `publish.ps1` 后**应当**手工跑一次语法检查 | 它自带的校验（`:120-131`）只 parse `updater/update_modpack.ps1`；`.github/workflows/release.yml:16-23` 也只校验那一个文件 | 与 §7"是否把 `publish.ps1` 纳入长期校验范围"是两件事 |
| 8 | 沿用 `upload_modpack.ps1` 的交互细节：模板由脚本预置、写完需在控制台确认 | 两侧体验一致，用户不必记两套操作 | 也可改成等记事本自行关闭 |
| 9 | **需新增失败检测**：对 `git push`、`gh release create` 判定退出码/异常，据此决定临时文件去留与提示 | §2 第 11 条依赖成功/失败判定，而当前实现没有 | **注意分支 a**：判定方式本身可能被 `EAP=Stop` + `2>&1` 反噬（§3.3），选实现时需验证；并需定义"`git` 成功而 `gh` 失败"的语义（见 §7 待确认项 4） |
| 10 | 用 `gh release create --notes-file <文件>` 代替 `--notes "$releaseNotes"` | 避免把整段日志当命令行参数传递（Windows 命令行有长度上限）；且临时文件此刻正在手上 | 需先写出一个**去掉 `#` 说明行**的临时文件（注意：**保留**那行时间戳，依据 Q19）；与 §1.3"不做用户入口"不冲突 |

### 验收前置（依据 §7 待确认项 5 的用户裁决：**就地验证 + 事后清理**）

- **日志内容由用户本人填写**（用户原话："更新日志让我来填 我要整活"）。开发 AI 不要把日志内容当固定测试数据。
- 用例 2–9、13 会真实创建 Release/tag，**共用一个不用于正式发布的版本号区间**。
- 每跑完一轮，需要清理**四样**：
  1. `gh release delete <tag> --repo Mashiro-Neri/RSTC-Updater --yes`
  2. `git tag -d <tag>`
  3. `git push --delete origin <tag>`
  4. **被推上去的提交**（`:138-139` 提交 + `:143` 推送 HEAD 会真的落在默认分支上）。二选一，**默认建议"提交还原"**：再提交一次把 `updater/update_modpack.ps1` 的 `UpdaterVersion` 改回原值并推送；备选是 `git push --force-with-lease` 改写历史（个人仓库风险低，但会改写公开历史）。
- **必须注意的死循环**：手工把版本号改回去会让工作区变脏，而 `publish.ps1:49-55` 会直接 `exit 1`。所以"还原版本号"**必须作为一次提交落下**（或先 `git stash` 后再跑），否则清理完就无法复测——这正是 §3.3 警告的"留下无法重跑的状态"。
- 清理后要确认 `UpdaterVersion` 已回到原值：它影响更新器的自更新判定（`:525`、`:535`；横幅在 `:148`）。**注意** `:818-819`、`:885` 读的是 `RSTC_version.txt` 并与**整合包 tag** 比较，与 `UpdaterVersion` 无关。

## 附录 B：客户端现有更新逻辑现状与风险清单（本轮不改）

**现状**

| 环节 | 做法 |
|---|---|
| 判断是否更新 | 本地 `RSTC_version.txt` 第一行与远端 tag **字符串全等**比较（`:818-819`、`:885`） |
| 下载 | 取 Release 的**第一个附件**当整合包，**每次全量下载**（`:172`、`:902`） |
| 同步范围 | 硬编码的 `mods, config, resourcepacks, shaderpacks, PCL`（`:13`，共 5 项） |
| 同步方式 | 逐目录 **`robocopy /MIR`**（镜像，会删目标多余文件）（`:373`） |
| 源目录不存在 | 跳过，本地旧目录**原样保留**（`:379`） |
| 根文件 | 只同步仓库根下有的文件，黑名单排除若干（`:381-388`） |
| 用户文件保护 | `options.txt`、`servers.dat`：**无条件**备份+还原（`:905`、`:921`）。`config/` 中"仓库没有的"文件：**仅当选择"保留本地配置"时**才备份+还原（`:906`、`:922`，均由 `if ($Script.PreserveConfig)` 守卫） |

**风险**（按严重程度）

1. `robocopy /MIR` 会**静默删除**用户放进 `mods`、`resourcepacks`、`shaderpacks`、`PCL` 的文件——这几类**没有任何保护**。而且 **`config/` 默认也不受保护**：`:870` 的菜单 `-Default 1` 指向"否 - 使用发布版文件覆盖"，`:872` 的 `PreserveConfig = ($cfgChoice -eq 0)` 因此默认为 false，于是**默认路径下 `config/` 里仓库没有的用户文件同样会被删掉**。只有 `options.txt`、`servers.dat` 是无条件保护的。
2. 同步目录**写死在客户端代码里**，新增整合包目录不会被同步，且要玩家先更新更新器本身才能生效。
3. 目录改名（如 `config` → `configs`）会导致本地**新旧并存**。
4. `assets | Select-Object -First 1` 不校验文件名（`:172`），多传附件可能下错文件。
5. 全量下载，整合包越大越痛（当前附件约 610 MB）。
6. 版本比较为字符串全等，本地版本文件被写坏成"未来版本"后**永远收不到更新**。

**已核实 —— zip 里实际有什么**（方法：对 `E:\其他文件\整合包上传\红石镇客户端 5.5.zip` 直接做二进制内容检索，见附录 C。检索前先做了**阳性对照**：`resourcepacks`（18 处）、`shaderpacks`（8 处）、`options.txt`（4 处）、`.disabled`（9 处）均能命中，确认该检索方法对 zip 内文件名有效）

| 检索项 | 结果 |
|---|---|
| `coremods` | **无匹配** |
| `defaultconfigs` | **无匹配** |
| `configureddefaults` | **无匹配** |
| `journeymap` | **无匹配** |
| `CustomSkinLoader` | **无匹配** |
| `kubejs` / `patchouli_books` / `ftbquests` / `scripts/` | **无匹配** |
| `mods/`、`config/`、`resourcepacks/`、`shaderpacks/` | 有 |
| 根目录文件（`options.txt` 等）、`*.disabled` 条目 | 有 |

**推论**：`客户端导出配置.txt` 只是一份**白名单**，只打包实例里**实际存在**的路径。上面那些目录不在包里，是因为该实例里没有它们。**更新器目前并没有漏同步任何实际存在的顶层目录**——它同步的 `mods`、`config`、`resourcepacks`、`shaderpacks` 恰好覆盖了包里实际存在的目录类。

> **因此风险 2 目前不成立，属未来风险**：只有在"实例里真的新增了这些目录（或 zip 里出现更新器不认识的顶层目录）"之后才会生效；届时因为同步目录写死在 `:13`、且要玩家先更新更新器本身，才会出现漏同步。
>
> **本项证据的边界**：这是"按文件名检索"得到的间接证据（能证明某名字**存在**，也能相当可靠地证明其**不存在**，因为 zip 的条目名是明文存于中央目录的），不是逐条列目录。若将来要做精确的同步目录清单，仍应以真实解包为准。
